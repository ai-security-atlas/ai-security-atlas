During autoregressive generation, [attention](../nodes/concept-attention.md) at each new token needs the keys and values of every earlier token. Recomputing them every step would be wasteful, so systems store them in a *KV cache* and reuse them. A related optimization, *prefix reuse*, keeps the cache for a shared leading portion of a prompt so it need not be recomputed across requests that begin the same way. Both are performance mechanisms; neither changes model outputs.

The consequence relevant to security is that a KV cache is *state that persists between computations*, and how it is scoped and shared is an implementation decision. When a cache is reused across requests, sessions, or tenants, isolation becomes a concern; and because reuse changes how much work a request does, it can introduce timing differences. These are considerations that depend on the deployment, not inevitabilities.

This concept is a prerequisite for both an attack and a defense side. It underpins [cross-session or cross-tenant disclosure](../nodes/attack-session-leak.md) and [prompt-cache timing inference](../nodes/attack-cache-sidechannel.md), where shared or observable cache behavior can leak information, and it motivates [cache and session isolation](../nodes/defense-cache-isolation.md) as a countermeasure. Whether a particular implementation is exposed to these effects should be assessed against the cited sources and the specific system.
