This technique induces repeated actions or delegated calls when an agent's execution lacks effective budgets, routing toward the objective of [degrading availability or increasing cost](../nodes/goal-availability.md). Rather than corrupting an answer, it aims to make the system spend unbounded work — the concern captured by the Unbounded Consumption category in current application-security guidance.

Conceptually the technique depends on the conditions that let iteration compound: [tool-using agents](../nodes/system-agent.md) that can invoke tools in a loop, and [multi-agent orchestration](../nodes/system-multiagent.md) where one agent can delegate to others recursively. The attacker-controlled input is whatever steers the agent toward more iterations or deeper delegation; the victim-controlled state is the orchestration logic and the absence of enforced limits. Where no budget caps the number of steps, tokens, or spawned sub-tasks, ordinary-looking requests can escalate into runaway consumption.

A useful distinction is that model reasoning cost, per-tool cost, and wall-clock limits are separate quantities that must be accounted for independently; a single global cap may not constrain all three.

The main candidate mitigation is enforcing [request, token, tool and cost budgets](../nodes/defense-budget.md), which bounds but does not by itself prevent inefficient or adversarial loops. Evaluation is framed through [attack success and severity](../nodes/eval-asr.md), an [explicit threat model](../nodes/eval-threat-model.md), and measured [query, token, latency and compute cost](../nodes/eval-cost.md). This attack belongs to the availability-and-cost family. For concrete consumption figures under specific configurations, defer to the cited sources.
