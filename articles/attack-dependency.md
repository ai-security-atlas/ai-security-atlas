This technique compromises an application through the code it imports — plugins, build dependencies, or executable repository code — rather than through the model's weights. It routes toward [compromising the surrounding execution environment](../nodes/goal-environment.md), aligning with the Supply Chain risk category, because untrusted code that runs in-process inherits the host's access.

Conceptually the technique depends on [model loaders and executable repository code](../nodes/system-loader.md) and on [tools, plugins, MCP and connectors](../nodes/system-tools.md): each is a place where third-party code executes as part of the AI application. The attacker-controlled input is the malicious package, plugin, or repository contribution; the victim-controlled state is the dependency graph and build pipeline that pulls it in and the runtime that executes it. A key framing is that traditional software supply-chain controls remain necessary around AI artifacts — the presence of a model does not displace the ordinary risks of importing code.

This sits in the supply-chain-and-runtime-compromise family and is a close relative of artifact substitution, though here the compromised object is code rather than the model package.

Candidate mitigations reduce but do not eliminate risk: a [least-privilege contribution and CI pipeline](../nodes/defense-ci.md) constrains who can introduce code and how it is reviewed, while [sandboxing, egress and execution isolation](../nodes/defense-isolation.md) limits what imported code can reach if it does run. Evaluation is framed through [attack success and severity](../nodes/eval-asr.md) under an [explicit threat model](../nodes/eval-threat-model.md). For documented incidents, defer to the cited sources.
