A trust boundary is any point where data, instructions, or authority pass from one principal or component to another — from a user to an application, from retrieved content into a model's context, from a model's output into a tool that can act. Authorization is the question of *what a given principal is permitted to do* once that crossing happens. Tracking these boundaries means knowing, at every step, whose data this is, whose instructions these are, and whose privileges are being exercised.

The recurring failure in AI systems is treating content as if it carried authority. When untrusted text — a web page, a document, a tool result — is read into the same context as trusted instructions, the model has no inherent way to tell them apart, and privileged actions can follow from unprivileged input.

This concept underpins a wide span of the atlas. It is a prerequisite for attacks such as [direct prompt injection](../nodes/attack-direct-injection.md), [indirect prompt injection](../nodes/attack-indirect-injection.md), [confused-deputy abuse](../nodes/attack-confused-deputy.md), and [cross-session or cross-tenant disclosure](../nodes/attack-session-leak.md), and for defenses including [separate data from authority](../nodes/defense-boundaries.md) and [enforce authorization outside the model](../nodes/defense-authorization.md). It is especially load-bearing for [tool-using agents](../nodes/system-agent.md) and [tools, plugins, MCP and connectors](../nodes/system-tools.md), where a crossed boundary can turn text into real-world action.
