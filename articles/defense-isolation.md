Sandboxing, egress and execution isolation constrain what model-adjacent code or agents can do when they run — limiting the actions they can execute, the files they can touch, and the network destinations they can reach. It applies where untrusted execution occurs, such as [model loaders and executable repository code](../nodes/system-loader.md), and works by confining that execution to a restricted environment with controlled outbound access, so that compromise is contained rather than free to spread.

This is a conditional, containment-oriented control. It can reduce the impact of [improper handling of model-generated output](../nodes/attack-output-sink.md), [malicious dependencies or repository code](../nodes/attack-dependency.md), and [unsafe checkpoint deserialization](../nodes/attack-unsafe-load.md) by ensuring that code triggered through these paths cannot freely execute commands, exfiltrate data, or reach sensitive systems. It does not prevent the initial compromise: it limits blast radius. Residual risk includes sandbox escapes, overly permissive egress rules, and actions that remain damaging even within the confined scope, and adaptive attackers probe for whatever the isolation still allows.

Because it contains rather than prevents, isolation is most effective layered with input-side controls like safer loading and dependency review. The cited guidance on privileged triggers and the threat knowledge base illustrate the execution paths this control is meant to box in.
