A least-privilege contribution and CI pipeline separates the handling of untrusted contributions from access to credentials, deployment, and executable builds. It rests on clear [trust boundaries and authorization](../nodes/concept-boundaries.md): inspecting or testing an outside contribution is treated as a lower-trust operation that must not run with the secrets or permissions reserved for trusted, reviewed changes. In practice this means untrusted code is evaluated in a constrained context, and privileged steps run only after human review has crossed the trust boundary.

This structure conditionally reduces supply-chain risk. It can limit [artifact, adapter or configuration substitution](../nodes/attack-artifact-substitution.md) and [malicious dependencies or repository code](../nodes/attack-dependency.md) by denying attacker-influenced content the credentials and deploy access needed to persist or propagate. It is a partial mitigation: misconfigured triggers that grant privileged tokens to unreviewed contributions, over-scoped runners, or secrets reachable from build steps all reopen the path, and it does nothing about malicious changes that pass review or dependencies compromised upstream.

The trade-off is friction and pipeline complexity against blast-radius reduction. It works best combined with provenance tracking and artifact verification. The cited guidance on privileged pull-request triggers details a common misconfiguration this control is designed to avoid.
