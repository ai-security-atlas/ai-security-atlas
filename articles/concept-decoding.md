Decoding is the step that turns a model's per-token scores into actual generated text. At each position the model produces [logits](../nodes/concept-logits.md); decoding configuration decides how those scores become a chosen token. *Temperature* rescales the distribution, making it flatter (more varied) or sharper (more deterministic). *Selection rules* — such as greedy choice, top-k, or nucleus sampling — restrict which candidates are eligible. *Stopping conditions* determine when generation ends, via end-of-sequence tokens, length limits, or stop strings.

The defining property is that all of this operates *at inference time and changes outputs without retraining*. The same weights, under different decoding settings, can yield confident and repetitive text or diverse and exploratory text. This distinguishes decoding from training-time factors: it is a knob on how the fixed model is sampled, not a change to what the model has learned.

Because it requires access to or assumptions about logits, decoding sits directly downstream of that concept. For a security engineer, decoding configuration matters because it shapes reproducibility and the diversity of outputs an attacker or evaluator observes; the same prompt may behave differently under different settings. The specific ways decoding interacts with particular attacks or defenses belong to those techniques, and empirical effects should be drawn from cited sources rather than assumed.
